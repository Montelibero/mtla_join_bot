# MTLA Join Bot: актуальная спецификация процесса

Этот документ описывает целевое и реализованное поведение пользовательского
процесса. Подробный аудит, известные эксплуатационные ограничения и план работ:
[`docs/audit-2026-07-18.md`](docs/audit-2026-07-18.md).

## Граница процесса

Бот проверяет минимальные формальные условия и сообщает кандидату, что тот готов
самостоятельно подать заявление через бота обратной связи Монтелиберо.

Бот не:

- доказывает владение Stellar-адресом;
- подаёт заявление автоматически;
- принимает решение о вступлении;
- отслеживает рассмотрение заявления.

## Обязательные правила

Кандидат готов к подаче, только если одновременно:

1. выражено согласие с Соглашением;
2. указан существующий обычный Stellar G-адрес с корректной контрольной суммой;
3. на адресе открыта линия доверия к точному настроенному MTLAP asset;
4. текущий MTLAP-баланс кандидата равен нулю;
5. в BSN есть хотя бы одна входящая `RecommendToMTLA`;
6. текущий баланс точного MTLAP asset хотя бы у одного рекомендателя не меньше 2.

Telegram username не входит в eligibility. При его отсутствии бот настоятельно
рекомендует установить username и даёт явную кнопку продолжения без него.

Любой положительный MTLAP-баланс кандидата ведёт в отдельный ответ
`ALREADY_MEMBER`, а не к завершению процесса.

## Попытка и команды

- `/start` всегда создаёт новую попытку и сбрасывает текущий прогресс.
- `/restart` полностью эквивалентен `/start`.
- Возобновления старой попытки нет.
- Новая попытка получает случайный `attempt_id`.
- Inline-callback имеет форму `flow:<action>:<attempt_id>` и принимается только
  в ожидаемой фазе той же попытки.
- `/language` меняет язык и перерисовывает prompt текущей фазы.

Закрытие приложения Telegram технически не наблюдаемо ботом. Оно не является
серверным событием и не меняет MongoDB само по себе.

## Состояния

| Состояние | Ожидаемое действие | Следующее состояние |
|---|---|---|
| `checking_username` | Проверка username или явное продолжение без него | `agreement` |
| `agreement` | Согласие с Соглашением | `entering_address` |
| `entering_address` | Ввод Stellar-адреса | `checking_address` или `finalizing` |
| `checking_address` | Исправление условий и повторная проверка | `checking_address` или `finalizing` |
| `finalizing` | Доставка финального ответа; при сбое её можно повторить | `completed` |
| `completed` | Терминальная попытка | только новый `/start` |

Все значимые переходы MongoDB условны по `user_id`, `attempt_id` и ожидаемому
состоянию. Результат внешней проверки старой попытки не может быть записан в
новую попытку.

## Внешняя проверка

Один ввод адреса создаёт один согласованный snapshot:

1. Horizon возвращает аккаунт кандидата и его balances.
2. Если аккаунта нет, это бизнес-ответ «адрес не существует».
3. Если Horizon недоступен или ответ повреждён, это временная техническая ошибка.
4. Для кандидата запрашивается только
   `GET /accounts/{candidate}?format=json&tag=RecommendToMTLA` в BSN.
5. BSN response проверяется по размеру, структуре, `account.id`, счётчикам ссылок
   и допустимому same-origin redirect.
6. Для найденных рекомендателей Horizon проверяется с ограниченной
   параллельностью; сравнение баланса выполняется через `Decimal`.

Перед внешним запросом пользователь получает видимое сообщение о начавшейся
проверке. Холодный per-account BSN может отвечать десятки секунд, поэтому ему
даётся одна попытка до 25 секунд без немедленного повтора того же тяжёлого
запроса; общий deadline проверки — 35 секунд. Horizon использует более короткие
четырёхсекундные запросы с ограниченным retry.

Отсутствие рекомендации, недостаточный баланс и недоступность BSN/Horizon — три
разных результата. Технический сбой не записывается как «условие не выполнено».

## Сохранение результата и доставка

После успешного snapshot MongoDB одной условной записью сохраняет:

- Stellar-адрес;
- согласие;
- наличие trustline;
- канонический нулевой MTLAP-баланс кандидата;
- наличие квалифицированной рекомендации;
- состояние `finalizing`.

Затем бот отправляет финальный текст: пользователь молодец, проверки пройдены и
можно подать заявление в `@mtl_helper_bot`. Только после успешной отправки
попытка условно переводится в `completed`, вместе с идентификатором Telegram
message. Если доставка не удалась, `finalizing` сохраняется и бот предлагает
повтор. Если ответ доставлен, но MongoDB временно не подтвердила `completed`, бот
не присылает противоречащую ошибку; durable `finalizing` допускает повторную
доставку. Фоновый worker после восстановления сервиса и после перезапуска
подбирает такие записи ограниченными пачками. Перед отправкой он атомарно берёт
lease и увеличивает счётчик; одновременно отправлять один финал нельзя, а после
трёх записанных попыток фон больше не отправляет сам. Кандидат всё ещё может
явно повторить только доставку кнопкой,
не проходя проверки заново. Семантика доставки at-least-once: при
сбое ровно между Telegram send и Mongo commit возможен повтор финального
сообщения. Исчерпанные или нарушающие инварианты записи остаются видимыми
администратору, но не спамят кандидата и не блокируют более новые доставки.

## Ошибки и конкурентность

- Необработанная ошибка handler-а получает безопасный пользовательский
  `temporary_error`, если Telegram ещё доступен.
- Updates, накопленные во время короткого downtime, не удаляются при запуске.
- Бот обрабатывает до восьми updates параллельно между разными пользователями.
- Пока действие пользователя выполняется, следующий обычный update этого же
  пользователя не ждёт внутри глобального лимита, а получает явный ответ.
- `/start` и `/restart` отменяют активную in-memory проверку пользователя и
  начинают новую попытку; MongoDB-условия дополнительно отсекают устаревшую
  запись, если отменённая операция уже дошла до storage.
- Синхронный PyMongo выполняется вне event loop с ограниченными connection и
  operation timeout, поэтому зависшая база не замораживает ответы всем сразу.
- Неожиданный текст не игнорируется молча.

Long polling рассчитан на один экземпляр бота. Запуск нескольких экземпляров
требует отдельной координации доставки Telegram updates и финальных сообщений.

В Docker bot и MongoDB работают отдельными Compose services. MongoDB имеет
healthcheck и отдельный сохраняемый volume; удаление volume допускается только
явно подтверждённой командой `clean` после backup.
Обычный `run` не создаёт отсутствующий volume молча: для действительно новой
установки требуется отдельная явная команда `bootstrap`.

## Команды администратора

- `/stats`
- `/incomplete`
- `/reminders [дни]`
- `/user_info <user_id>`
- `/help_admin`

Сбой чтения MongoDB не интерпретируется как пустой список или нулевая
статистика: администратор получает явный ответ о временной недоступности.
